# 迭代工作流（所有 AI 必须遵守）

> 本文档是**操作规范**，不是说明文。
> 在 Figma 设计稿上做任何迭代之前，先完整读一遍。
> 违反命名规范或跳过提问步骤，会让版本历史失去可追溯性。

---

## 0. 一句话流程

```
新会话开始：运行 ./fimg page check 检查页面版本状态
  ├─ 【分流 1 · 历史清理】：若存在早于最新 release 的历史 beta → 先提示用户是否删除历史 beta
  ├─ 【分流 2 · 迭代决策】：若已有进行中的 beta（日期晚于/同步于最新 release）：
  │    必须询问用户：是否要新创建一个 beta？
  │    ├─ 用户选「新建」：递增创建 beta.N 页面（如 beta.2）
  │    └─ 用户选「不新建」：直接在已有 beta 页面上就地迭代改动（严禁每次交互都新建页面！）
  └─ 【分流 3 · 干净基线】：若当前仅有已发布 release 页面：
       询问用户是否基于最新 release 创建首个 beta.1 页面开启迭代
在确认的 beta 页上改稿，边改边标注
  → 用户确认完成后 promote 成 release，删掉本轮 beta 页
```

## 1. 页面命名规范

| 阶段 | 格式 | 示例 |
|---|---|---|
| **release** | `YYYY-MM-DD-主题` | `2026-10-04-列表可读性` |
| **beta** | `YYYY-MM-DD-主题-beta.N` | `2026-10-04-列表可读性-beta.1` |

硬性规则：

1. **release 不带任何后缀**，也不留尾部短横线。
   ❌ `2026-10-04-列表可读性-release`　❌ `2026-10-04-列表可读性-`
   ✅ `2026-10-04-列表可读性`
2. **beta 必须带 `-beta.N`**，N 从 1 开始递增（beta.1 → beta.2 → …）。
3. 日期是**迭代启动日**（创建 beta 页当天），不是发布日。
4. 主题用简短中文（2–6 字），能一眼看出改了什么。避免空格，用短横线连接多词。
5. 同一主题的多个 beta 使用**同一日期与主题**，只递增 N。

---

## 2. 新页面位置

**所有新建页面插入到文档最上方**（index 0）。

理由：迭代稿永远在最前，打开文件第一眼就是最新状态；历史稿按时间往下排。
插件的 `page create` 默认就插到最上方（`--no-top` 可关闭，一般不要用）。

## 3. 开始一轮迭代与新会话检查（必须按策略提问）

**触发时机**：新会话开始、或用户明确提出要迭代/改稿时。

> ⚠️ **严禁每次交互无脑新建一个 page！**
> 必须先执行 `./fimg page check` 对比当前文档中最新的 Release 页面与 Beta 页面，按以下三类分支决策：

### 第一步：运行页面检查
```bash
./fimg page check
```

### 第二步：根据三类分流情况提问用户

#### 分流 1：检测到历史残留 Beta 页面（Beta 日期早于最新 Release）
> **场景说明**：文档中存在上次发布之前的历史遗留 beta（`beta 日期 < latest release 日期`）。
- **必须先向用户提示并确认清理**：
  > “检测到当前文档存在历史残留 Beta 页面：`[历史Beta页面名]`（早于当前最新已发布版本 `[最新Release名]`）。请问是否先删除这些历史过期 Beta 页面？”
- 用户确认删除后，执行 `./fimg page delete --name "..." --confirm` 完成清理；清理完毕后再引导用户基于最新 Release 开启新迭代。

#### 分流 2：已有进行中的有效 Beta 页面（Beta 日期晚于或等于最新 Release）
> **场景说明**：当前文档已有一个处于进行中迭代状态的 Beta 页面（如 `2026-10-18-主题-beta.1`，其日期晚于或等于最新 release）。
- **必须用提问工具向用户询问**：
  > “检测到当前已有进行中的迭代页面「`[当前最新Beta名]`」。请问本轮修改：
  > 1. 是需要新创建一个递增的 Beta 页面（如 `[...-beta.2]`）备份阶段成果？
  > 2. 还是直接在已有的「`[当前最新Beta名]`」页面上继续修改？”
- **执行规则**：
  - **用户选择新建**：执行 `./fimg page create --name "...-beta.(N+1)" --copy "...-beta.N"`，并在新页面改稿；
  - **用户选择不新建**：**直接将后续写操作指向该已有 Beta 页面（`--page "..."`）并在其上改稿**，**严禁再次创建新页面**！

#### 分流 3：当前文档仅有 Release 页面（无任何 Beta 页面）
> **场景说明**：文档处于刚刚 Promote 发布后的干净状态，不存在任何活动的 Beta 页面。
- **向用户询问基准与主题**：
  > “当前文档仅有已发布的基准页面「`[最新Release名]`」。请问本轮迭代的主题是什么？我将为您基于该基准创建首个 `[YYYY-MM-DD-主题-beta.1]` 页面开始改稿。”
- 用户确认后执行 `./fimg page create --name "$NAME" --copy "$基准页"`。

## 4. 迭代过程中的标注（强制）

**每一处对设计稿的修改，都必须在不遮挡稿件的前提下留下可追溯的标注。**

### 标注的形态

标注块命名统一为 `FIMG·标注`（迭代汇总面板叫 `FIMG·迭代说明`）：

```jsonc
{
  "type": "FRAME", "name": "FIMG·标注",
  "layout": "V", "w": 200, "h": "hug", "gap": 4,
  "pad": 10, "fill": "#FFF7E6", "radius": 6,
  "stroke": "#F0A020", "strokeWeight": 1,
  "x": 0, "y": 900,          // ← 坐标由下方「放置策略」决定
  "children": [
    { "type": "TEXT", "text": "修改 · 列表可读性", "size": 11, "weight": 600, "color": "#B25CE0" },
    { "type": "TEXT", "text": "名称 15→16\n代码色 #8A9099→#6B7280", "size": 10, "color": "#16181D" }
  ]
}
```

内容格式固定：

- 第一行：`修改 · <主题>`
- 后续行：**逐条**写清楚改了什么（字段 · 旧值 → 新值）
- 一次 `patch` 改了多处可合并到同一标注；**不同屏幕的改动各放一个标注**

### 放置策略（三档，从优到劣）

稿件是主内容，标注是辅助内容。**先量密度，再选档位。**

#### 前置：量出稿件的包围盒

```bash
./fimg dump --depth 0 --page "<目标页>" --out dumps/layout.json
```

读每个顶层 Frame 的 `x/y/w/h`，算出全体稿件的包围盒
`content = { minX, minY, maxX, maxY }`。**任何标注的矩形都不得与现有 Frame 相交。**

#### 档 1 · 邻接空隙（稿件少、四周有空白时）

在被改屏幕的**四边**依次尝试放置（标注宽约 200、高按内容估 80–160）：

| 优先 | 位置 | 坐标 |
|---|---|---|
| 1 | 正下方 | `x=屏.x`，`y=屏.y+屏.h+56` |
| 2 | 正上方 | `x=屏.x`，`y=屏.y-标注高-56` |
| 3 | 左侧 | `x=屏.x-标注宽-56`，`y=屏.y` |
| 4 | 右侧 | `x=屏.x+屏.w+56`，`y=屏.y` |

候选矩形与任何已有 Frame **无相交**就用它；四边全撞则进档 2。

```
y=0     ┌────────┐ ┌────────┐ ┌────────┐
        │ 01 行情│ │ 02 详情│ │ 03 详情│
y=844   └────────┘ └────────┘ └────────┘
y=900   ┌标注┐     ┌标注┐                 ← 档 1：屏幕下方空隙
```

#### 档 2 · 标注带（中等密度，一排屏下面有整条空白）

当 `content.maxY` 之下（或右侧）存在**整条空白带**（宽 ≥ 200 或长 ≥ 3 屏），
把标注统一放进这条带：

- **底带**：`x` 与被改屏左对齐，`y = content.maxY + 56`，同屏多条沿 y 向下堆叠
- **右带**：`y` 与被改屏顶对齐，`x = content.maxX + 56`，同屏多条沿 x 向右堆叠

```
y=0         ┌────┐ ┌────┐ ┌────┐ ┌────┐
            │ 屏 │ │ 屏 │ │ 屏 │ │ 屏 │
y=2400      └────┘ └────┘ └────┘ └────┘
y=2456      ┌标注┐  ┌标注┐               ← 档 2：底部标注带
```

#### 档 3 · 专属面板 + 指示（高密度，四五十屏横竖铺满时）

**四五十屏的页面不要在屏间挤标注**。直接单开一块迭代说明面板，
用**角标 + 连接线**指回被改的屏：

1. **面板位置**：`x = content.maxX + 120`（右侧一列），宽 320；
   若右侧也满，则 `y = content.maxY + 120`（底部一行）。
   面板名 `FIMG·迭代说明`，内含本轮**全部**标注条目（每屏一节）。

2. **被改屏角标**（必做）：在每个被改屏幕的**右上角内侧**放一个
   12×12 的实心圆点（`ELLIPSE`，色 `#B25CE0`，命名 `FIMG·角标`），
   `positioning:"ABSOLUTE"`，`x=屏.w-24, y=16`。

3. **连接线**（推荐，面板离得远时必做）：从面板边缘拉到角标——
   一条 2px 高的细 `RECT`（或 `LINE`），`rotate` 设为两点连线的角度，
   色 `#B25CE0`，命名 `FIMG·连线`。
   角度算法：`角度 = atan2(dy, dx) 的度数（顺时针为正）`；
   长度 `= sqrt(dx²+dy²)`。画不准就退而求其次：在面板条目里
   写明 `→ 12 行情`（屏幕名），角标已经足够指认。

```
                    ┌─────────────────────────┐
    ┌────┐ ┌────┐   │  FIMG·迭代说明           │
    │ ●屏│ │屏 ●│───│  12 行情: 名称 15→16      │
    └────┘ └────┘   │  24 详情: 按钮字 14→15    │
    ┌────┐ ┌────┐   │  38 设置: 新增「保存」    │
    │屏  │ │  ●屏│───└─────────────────────────┘
    └────┘ └────┘      ▲ 连接线 · 紫色 ●=角标
```

### 标注的时机

- **边改边标**：每完成一批 `patch`，立即放对应标注 / 角标
- 不要等全改完再补——那时你已经记不清改过哪些

### 其他硬性约束

- 标注插入到**页面层级**（`--parent <pageId>`），不要插进屏幕 Frame 里
  （屏幕是 auto-layout，会把标注当内容排版）
- **任何标注/面板/连接线的矩形都不得与已有 Frame 相交**——
  放之前用 `dump --depth 0` 量一遍，放之后再量一遍确认
- `name` 前缀固定 `FIMG·`（标注 / 角标 / 连线 / 迭代说明），方便批量清理

## 5. 迭代结束 → 发布

用户明确说「迭代完成 / 可以了 / 发布吧」时：

```bash
# 1. 汇总：把最终 beta 升为 release（去掉 -beta.N 后缀）
./fimg page promote --name "$最终beta页名"

# 2. 删除本轮所有 beta 页（包括中途的 beta.1、beta.2 …）
./fimg page delete --name "…-beta.1" --confirm
./fimg page delete --name "…-beta.2" --confirm
# … 逐个删，或列出本轮所有 beta 一起删
```

**注意**：

- `promote` 默认会把 release 页插到最上方
- 若 release 名已存在且内容过时，用 `promote --force` 覆盖（会删除旧 release）
- **beta 页删掉后不可恢复**——删除前确认用户真的要发布
- 保留 `FIMG·标注` 在 release 上是有价值的（版本变更记录）；
  若用户要求干净交付，最后再统一 `rm --name "FIMG·标注"`

## 6. 命令速查（迭代全过程）

```bash
./fimg page check                                   # 0. 新会话必跑：检查最新 release 与 beta 状态
./fimg page list                                    # 1. 看有哪些页、当前页
./fimg page create --name X --copy Y                # 2. 建 beta（复制基准页，插到最上）
./fimg dump --name "卡片名" --out dumps/x.json      # 3. 读现状
./fimg patch --ops ops.json --dry                   # 4. 先看审计
./fimg patch --ops ops.json --page "X-beta.1"       # 5. 真改（写操作都带 --page！）
./fimg insert note.json --parent <屏幕id>           # 6. 放标注
./fimg export --names "屏幕名" --page "X-beta.1"    # 7. 截图核对
./fimg page promote --name "X-beta.1"               # 8. 发布
./fimg page delete --name "X-beta.1" --confirm      # 9. 清理 beta
```

## 7. 禁止事项

| 禁止 | 原因 |
|---|---|
| **每次交互无脑新建一个 beta 页** | 会导致文档页面泛滥失控。每次新会话必须询问是否新建；用户若不新建，必须在已有 beta 页上就地改动 |
| **忽略早于 release 的历史 beta** | 会造成过时草稿混淆，新会话检测到时必须先提示用户是否清理 |
| 不问基准页和主题就开干 | 改错页面 / 命名不可追溯 |
| 在 **release 页**上直接改稿 | 会破坏已交付版本；一律新建 beta |
| 新建页插到文档末尾 | 打开文件找不到最新稿 |
| 命名带 `-release` 或尾部 `-` | 污染版本语义 |
| 改了稿不标注 | 审阅时看不出改过什么 |
| **标注/面板/连线与任何稿件矩形相交** | 挡住主内容。放之前量包围盒，放之后复查 |
| 高密度页面还在屏缝里挤标注 | 四五十屏的页一律走档 3（面板+角标） |
| 用户没确认就删 beta | 删掉就没了 |
| 用 `render` 重画已有设计稿 | 会丢图层结构；迭代一律 `patch` |
